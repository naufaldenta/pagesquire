# Public API review baseline

This page lists PageSquire's public integration surfaces and describes the automated check that catches unreviewed API changes. It is not an API freeze. PageSquire is at `0.1.0-beta.0`, and any contract can still change in a documented prerelease. See [beta](beta.md) and the [maintenance policy](maintenance.md).

## Integration surfaces

Recent additions, newest first:

- **Action progress.** Core progress event, stage, code and listener types, with optional runtime-wide and per-call callbacks. Client: required `ChatState.actionProgress`, `ActionTimelineEntry` and `describeActionProgress`. Hand-built typed states must supply an empty list, and matching assets are needed. The widget's busy DOM selector is now `data-busy`, and the message log's `aria-busy` no longer silences the status next to it. Protocol, storage and permissions are unchanged. See [action progress](action-progress.md).
- **App context.** Core `AppContext` and its field options, `RuntimeOptions.appContext`, `readAppContext()`, protocol context and status types and schema, and `validateAppContext`. `ChatRequest.appContext` is optional. The JavaScript and PHP semantic validators enforce uniqueness and byte limits beyond the structural checks, and Laravel keeps the validated context. Old requests stay valid, but older servers with closed schemas reject requests that include it, so deploy servers first. This is a wire extension, not just a local helper. Storage formats and authorization are unchanged. See [app context](app-context.md).
- **Capability inspector.** Optional `CapabilityInspector` and inspection types in core, and `mountInspector` in client. Local development diagnostics only: existing constructors, protocol and storage formats, runtime permissions and provider policy are unchanged. Inspector diagnostics schema `1` is not a wire-protocol change. See [capability inspector](capability-inspector.md).
- **Screenshots.** Optional `ActionResult.screenshot` with `Screenshot`, `Verification.screenshot`, `InputDriver.screenshot`, `createScreenshotCapabilities`, server `EngineOptions.screenshots`, `ProviderImageMessage` (providers now receive `(ProviderMessage | ProviderImageMessage)[]`) and the `screenshots` option of `siteDeclaration`; the PHP engine's `screenshots` argument and the second argument of `ActionSigner::declaration`; and Laravel `companion.screenshots`. Update servers before browsers that send screenshots.
- **Session tabs.** Optional `PageSnapshot.tabs` with `TabSnapshot`, `ObserverOptions.remoteTabs`, `InputDriver.switchTab`, `CompanionDriver.tabs`, and the generic `ui.switch_tab` tool, which is part of the generic manifest. Update servers before browsers that send tabs.
- **Cross-origin frames.** Optional `PageSnapshot.frames` with `FrameSnapshot`, `ObserverOptions.remoteFrames`, `InputDriver.frameTarget` and `frameAct` with `FrameTargetInfo`, `FrameActRequest` and `FrameEffect`, and `CompanionDriver.frames`. Update servers before browsers that send frames, because older servers reject the field.
- **Signed action calls.** Optional `ActionCall.signature` and `ActionCallSignature`; server `EngineOptions.signing`, `ActionSigning`, `SignatureClaims`, `SIGNATURE_CONTEXT`, `SIGNATURE_TTL_SECONDS`, `createSigningKey`, `signingPublicKey`, `checkSigning`, `signActionCall`, `verifyActionCall` and `siteDeclaration`; the PHP `ActionSigner` class and engine `signer` argument; Laravel `companion.signing_key` and `companion.origin` config with the `pagesquire.declaration` route; and the `signing-key` CLI command. Update browsers before servers start signing, because older clients reject the field.
- **Companion extension.** Core `InputDriver`, `GenericOptions.driver`, `createCompanionDriver`, `CompanionOptions`, `CompanionDriver` and `COMPANION_PROTOCOL`, and the embed's `data-companion` attribute. Messages between the page and the extension are versioned separately (`version: 1`) and documented in the [companion extension](companion-extension.md#wire-format) guide. The development extension itself is not a published package.
- **Visitor prompts and plans.** Optional `AssistantResponse.plan` (2–5 strings, sent only when an engine enables `plan`); core `VisitorPrompt` and `VisitorRequest`, `RuntimeOptions.visitor` and `visitorTimeoutMs`, `ExecutionContext.askVisitor`, the `VISITOR_DECLINED`, `VISITOR_TIMEOUT` and `VISITOR_UNAVAILABLE` codes, `ui.ask` and `ui.hand_off`, `ObserverOptions.outline` and `frames`; client `createVisitorPrompt`; engine `plan` and `checkActions` options and `planSteps` (Node and PHP); Laravel `limits.plan` and `limits.check_actions`; the progress argument of Laravel `HandleChat::handle`; and the `plan` trace field. Update browsers before enabling `plan`, because older clients reject the field.
- **Streaming.** Protocol `SERVER_PROGRESS_STAGES`, `ServerProgressStage`, `ChatStreamEvent` and `CHAT_STREAM_TYPE`; an optional `onProgress` argument to Node and PHP `ConversationEngine.handle`, PHP `ChatEndpoint::handle` and the client `ChatTransport`; PHP `ChatEndpoint::stream`; the transport `stream` option; `ChatState.serverStage`; and `server` trace events. Non-streaming requests and responses are unchanged.
- **Languages.** Client `en`, `id`, `locales`, `Locale`, `Messages`, `MessageKey`, `LocaleOptions`, `localeFor`, `resolveMessages` and `format`; `locale` and `messages` options on the widget, transport, client, approval prompt and guided tour; an optional `messages` argument to `describeActionProgress`; Node `ENGINE_TEXT`, `EngineLocale` and `EngineOptions.locale`; and PHP `ConversationEngine::TEXT` with a `locale` argument. The browser follows `<html lang>` by default, and the server stays in English by default.
- **Completion validator, trajectory cache and typed-data screening.** Node `EngineOptions.validateCompletion` and `trajectoryCache`, `TrajectoryCache`, `MemoryTrajectoryCache`, `CachedStep` and `CachedTrajectory`, `trajectoryKey` and `unrequestedData`; PHP `validateCompletion` and `trajectoryCache` engine arguments, `TrajectoryCache`, `MemoryTrajectoryCache`, `ConversationEngine::unrequestedData` and `trajectoryKey`; Laravel `CacheTrajectoryCache` and config keys; and `ConversationState.replay` and `recording`. A generic `ui.type` proposal with contact data, links or long numbers the visitor did not give now ends the turn.
- **Tracing.** Client `TraceEvent`, `ClientOptions.onTrace`, `TraceRecorder` and `mountTraceViewer`. Snapshot truncation now keeps on-screen targets first.
- **Generic actions and observation v2.** Optional snapshot fields (state flags and `new` on `ObservedTarget`, `PageSnapshot.removedTargets`), the `PageObserver.find` and `observableUrl` helpers and `composedClosest`; core `createGenericCapabilities`, `createGenericBindings` and `defaultRisk`; `ExecutionContext.requestApproval`; new progress codes; `EngineOptions.maxRecoveries`, the PHP `maxRecoveries` argument and Laravel `limits.max_recoveries`; client `allowRecovery`; and `ConversationState.recoveries` and `failedCall`. Snapshot target IDs are now stable across snapshots. Deploy servers before browsers that send the new optional fields.
- **WebMCP and approvals.** Core `exposeToWebMcp` and WebMCP types, `RuntimeOptions.approve` and `approvalTimeoutMs`, `ApprovalRequest`, `BrowserRuntime.approvalEnabled`, the `APPROVAL_DENIED` and `APPROVAL_TIMEOUT` progress codes, client `createApprovalPrompt`, `EngineOptions.allowConsequential` and the PHP `allowConsequential` constructor argument, Laravel `allow_consequential` config, and WordPress `Abilities`. All opt-in; protocol `0.1` is unchanged.
- **Provider tools mode and diagnostics.** The `tools` response mode; `ProviderDiagnostic`, `onDiagnostic` and `toolNames` in Node; optional `capabilities` and `config` arguments to `completionRequest`, `decodeCompletion`, `CompletionCodec::request` and `CompletionCodec::decode`; `CompletionCodec::usage` and `toolNames`; `ProviderHttpException` from the native cURL client; an optional `onDiagnostic` argument on the native PHP provider; and the Laravel `ProviderCalled` event. Defaults and protocol `0.1` are unchanged.
- **Hardening.** Optional `PageObserver` options `observeUrl` and `redactUrl` and `observableUrl()`; `BrowserRuntime.resetSession()` (called by `AssistantClient.reset()`; hand-built runtime doubles must add it); an optional `attemptsPerHour` limit on the handler and endpoint, with an optional `budget` field in the stored session; and Laravel `ChatRequest::payload()`. Protocol `0.1` fields are unchanged. Behavior changes: conversation history no longer stores the `observation` snapshots of results, oversized contexts are not charged, sessions default to 60 provider attempts per hour, and more sensitive query keys are rejected.
- **Assistant driving.** Optional core helpers for presentation, controls and reading, `ExecutionContext.present`, `PageObserver.readContent`, and client tour and speech helpers. Real runtime contexts get `present` automatically; hand-built typed contexts and mocks must add it. The WordPress plugin has new optional built-ins. Protocol `0.1` fields, storage envelopes, action permissions and the provider retry policy are unchanged. See [assistant driving](assistant-driving.md).

Use the package entry points and the integration guides, not private build paths. The exported types are the authoritative signatures. The table below describes what each surface is meant to offer; it does not promise that every class or option is stable.

| Surface                                                     | Intended integration contract                                                                                                                                                                                                           |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@pagesquire/protocol` and `@pagesquire/protocol/schemas/*` | Protocol `0.1` requests/replies/actions/snapshots, capability/provider schemas, validators, emotion types/normalization. Package release version and wire schema version are separate.                                                  |
| `@pagesquire/core`                                          | Registry/bindings, browser observation/runtime, execution and verification, navigation adapters and explicit control helpers. Host permissions and actual postconditions remain mandatory.                                              |
| `@pagesquire/client` and `@pagesquire/client/widget.css`    | `AssistantClient`, same-origin HTTP transport, widget mounting/options, navigation continuation and emotion callbacks. Stylesheet entrypoint is public; private DOM selectors/internal CSS details are not a styling stability promise. |
| `@pagesquire/react`, `/inertia`, `/next`                    | `PageSquireWidget`, `createInertiaNavigation`, `createNextNavigation` and their declared props/options. Host router/session/auth integration remains host-owned.                                                                        |
| `@pagesquire/cli` and `pagesquire` binary                   | Documented onboarding commands, config/mapping validation and exported workflow helpers. It does not discover everything, grant permissions or guarantee what a coding agent does.                                                      |
| `@pagesquire/server`                                        | Engine/provider/configuration interfaces, handler authorization, serialized store transactions and trusted `forgetConversation`. Public export visibility does not promise a stable on-disk conversation format.                        |
| `pagesquire/server` / `PageSquire\Server\`                  | Composer platform/namespace boundaries and documented native PHP engine, provider, endpoint/store/privacy interfaces. Only trusted host integrations may supply identity, storage and provider settings.                                |
| `pagesquire/laravel` / `PageSquire\Laravel\`                | Service-provider registration, published configuration, catalog/provider binding and documented named route/gates. The adapter's cache envelope is not interchangeable with the native endpoint.                                        |
| WordPress ZIP                                               | Documented administrator setup, data-only mappings, selected public-page capabilities and server-side provider configuration. Prefixed vendor classes, option keys, locks and internal plugin methods are not a stable extension API.   |

Provider presets, configuration, environment variables and their older aliases are documented in [providers](providers.md). The model is always chosen by the site owner; the API check says nothing about model accuracy or provider availability. Required host versions are listed in [compatibility](compatibility.md).

## What the automated check measures

```sh
npm run build
npm run api:check
```

`docs/api-baseline.json` records the package version and normalized SHA-256 fingerprints of:

- Selected npm manifests: names and module type, export maps and binaries, host engines, dependencies and peer requirements.
- All emitted `.d.ts` files in the six packages, including some internal declarations to be safe, and all exported protocol JSON schemas.
- Composer names and type, platform and dependency requirements, autoload and discovery, and suggestions.
- The PHP source trees and the WordPress entry file, fingerprinted **as whole source files**, not as parsed method signatures. A PHP change to an implementation or a comment can therefore require review.

Line endings (CRLF/LF) and JSON key order are normalized. The check fails on missing, changed or added declarations, schema changes, host or entry-point changes, a package version that drifted and PHP source changes. Linked inputs and baselines are rejected. The tool reads fixed paths in the checkout. It does not import JavaScript or PHP, boot a host, read production environment files, send telemetry or call a model. Run it in a trusted checkout that nothing else is writing to; it does not protect against a hostile process changing files at the same time.

The check runs as part of `npm test` and in Windows and Ubuntu CI after the build. Release candidate preparation also refuses to continue if the API has drifted, even when a fresh build fingerprint exists. New candidate manifests record `apiReview` as `review-baseline-not-frozen`.

A matching baseline only means the fingerprints match. It does not compare runtime behavior, decide a SemVer category, check CSS layout or freeze PHP public methods. Behavior, browser and security tests and code review are still needed.

## Reviewing intentional changes

1. Add a failing consumer, schema or behavior test. Compare the old and new declarations and schemas, the real package entry points and the required host versions. Decide explicitly whether the change is additive or affects behavior, the wire format, persistence or security; a hash cannot tell you.
2. Update the integration examples, the changelog, version and deprecation notes and the [upgrade guide](upgrading.md). For wire changes, review the closed schemas and how mixed browser and server versions behave. Do not quietly widen fields or permissions to keep an old client working.
3. Print the proposed baseline with `node scripts/check-api.mjs capture`. It only prints JSON; there is no automatic `--update` or approval command. Review the diff and replace the committed baseline yourself in the same reviewed change. Never update the baseline just to make CI pass.
4. Run the build, the API, type, contract and runtime checks, and clean consumer tests. Any change to an included source file or guide invalidates the candidate build fingerprint. Before publishing, check that CI passed on that exact commit.

`ConversationState`, the native, Laravel and WordPress storage envelopes, provider transcripts, lock, fence and option keys, replay-cache internals, private runtime fields, demo routes and assets, and generated binding internals are **not a stable interchange or backup format** across versions. Do not edit them by hand or pass them through a browser or model. [Upgrading](upgrading.md) describes the current tests that reopen state written in the same format. Broader state migration needs a durable format, version negotiation and tests against old releases, which do not exist yet.
