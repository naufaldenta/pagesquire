# C1 source review and extension priorities

This is a static architecture/source review, not a speed, accuracy or security benchmark. No competitor application or test suite was run and no source was copied into PageSquire. Inspected repositories were downloaded only to a separate temporary directory, not this repository. PageSquire's comparison baseline is `fefb680` with the D1 driving helpers already present.

## Priorities

1. **C2 — inspect the actual integration.** Compare expected capabilities to registered ones, diagnose sampled targets, expose existing schema/binding metadata and export only whitelisted diagnostics. Implemented locally in this source change; see [capability inspector](capability-inspector.md).
2. **C3 — explicit semantic app context and contextual availability.** Hosts supply typed, bounded public state and fixed-enum availability. Hints never replace server authorization. Implemented locally; see [context boundaries](app-context.md).
3. **C4 — truthful action progress.** Expose operational stages such as executing/verifying/verified and explain failures from actual runtime evidence. Implemented locally; see [progress, cache/navigation and recovery boundaries](action-progress.md). Existing thinking/emotion callbacks remain separate from per-action evidence.

Then prioritize from real user retests: reusable verified capability packs/parameter examples, redacted recorder-to-fixture workflows, typed read-result/source cards and curated host knowledge with citations. Approval/one-time authorization, undo, durable user-visible threads, generative UI and MCP/AG-UI bridges need separate protocol, privacy and security review. Do not postpone every independent user test until every idea is built.

Aliases, static/DOM coverage reports, bounded conversation continuation, six emotions, local-first speech, cursor presentation, public reading, tours and explicit per-action postconditions already exist in the baseline. They are not new gaps found by this review. Competitors can also perform outcome checks: PageSquire's focus is an explicit registered-action/postcondition contract across browser/Node/PHP/Laravel/WordPress integrations, not a claim that only PageSquire verifies results.

## Reuse and dependency boundaries

The inspected Pillar SDK is MIT; the platform is AGPL-3.0. CopilotKit, assistant-ui, Stagehand and Browser Use have MIT root licenses at the inspected revisions. Tambo has MIT client/UI/root material and Apache-2.0 core/backend/API sections. These are file-scope observations, not a blanket copying/redistribution conclusion; inspect each file and its notices before any future reuse. This implementation borrows concepts only and adds no competitor dependency or copied source.

Tambo also published a [hosted-service shutdown announcement](https://tambo.co/blog/posts/tambo-is-shutting-down). Its interactable design is a reference here, not a recommendation to adopt its hosted API. Recheck service and license status before making new dependency decisions.
