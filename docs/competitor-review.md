# Review of similar projects

This is a read-through of the source code of several open-source assistant and agent projects, done to decide what PageSquire should build next. It is not a speed, accuracy or security comparison: none of these projects were run, and no code was copied. The comparison was made against PageSquire commit `fefb680`, which already had the D1 driving helpers.

The separate Pillar platform was read at `0a414b84b52004bf682c51a416599ba3de9c3656`. Its legacy plans module says the plan execution system was removed, so it is not evidence of a current plan engine. Hosted or commercial features advertised next to these projects were not counted as part of their open-source packages.

## Priorities

1. **C2 – Inspect the real integration.** Compare expected capabilities with registered ones, check sampled targets, show schemas and binding metadata, and export only whitelisted diagnostics. Done; see the [capability inspector](capability-inspector.md).
2. **C3 – App context and contextual availability.** Hosts supply typed, bounded public state and a fixed set of availability values. These are hints and never replace server authorization. Done; see [app context](app-context.md).
3. **C4 – Action progress.** Show real stages such as executing, verifying and verified, and explain failures from what actually happened. Done; see [action progress](action-progress.md). The thinking and emotion callbacks stay separate from per-action results.

After that, priorities should come from real user testing. Candidates are reusable capability packs with parameter examples, turning recorded sessions into redacted fixtures, source cards for read results, and curated site knowledge with citations. Approvals, undo, persistent threads, generative UI and MCP/AG-UI bridges each need their own protocol, privacy and security design. User testing should not wait until all of these are built.

Aliases, static and DOM coverage reports, conversation continuation, six emotions, local speech, the cursor, public reading, tours and per-action postconditions already existed before this review. Other projects can check outcomes too. What sets PageSquire apart is one registered-action and postcondition contract shared across browser, Node, PHP, Laravel and WordPress.

## Licenses and dependencies

The Pillar SDK is MIT and the Pillar platform is AGPL-3.0. CopilotKit, assistant-ui, Stagehand and Browser Use have MIT root licenses at the reviewed commits. Tambo's client, UI and root are MIT, and its core, backend and API sections are Apache-2.0. These were checked per file, so check each file and its notices again before reusing anything. PageSquire borrows ideas only; it adds no dependency on these projects and contains none of their code.

Tambo has also announced that its [hosted service is shutting down](https://tambo.co/blog/posts/tambo-is-shutting-down). Its component design is used as a reference, not as a suggestion to adopt its hosted API. Check service and license status again before taking on any new dependency.
